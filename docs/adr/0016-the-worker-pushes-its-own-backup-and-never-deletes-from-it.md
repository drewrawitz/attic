# The Worker pushes its own backup every night, and never deletes from it

What Cloudflare keeps does not outlive the account. D1 Time Travel reaches back 7 days on Workers Free, covers no file in R2, and is gone with the database (ADR 0012). Filling an Attic takes hours of interviews, so a copy of the data has to leave Cloudflare. Four things about that copy are hard to change once there are backups that follow them:

- **The Worker pushes the backup itself, every night.** A Cron Trigger fires the Worker's `scheduled` handler. It asks Cloudflare's API for an export of the database and streams the SQL file into the backup bucket: any S3-compatible bucket at another provider, which the User sets up and names in the settings. Nothing outside Cloudflare has to run, be awake, or hold a Cloudflare token.
- **Attic never deletes from the backup bucket.** It writes there, and reads back the one object it keeps for itself. An export is named by its date, as in `database/2026-10-14.sql`, so a second run on the same day replaces that day's export and no run touches another day's. How long an export is kept is a lifecycle rule at the provider. A file is copied to `files/<its key in R2>`, and one that is deleted from R2 stays in the backup. So the access key can be one that cannot delete, and neither a bug in Attic nor an access key that leaks can empty the backup.
- **What the backup knows about the bucket is kept in the bucket.** The copy of the files remembers how far it got in a cursor: the key of the last file it copied, in one small object in the backup bucket, `state/files-cursor.json`. A run reads the cursor, lists R2 after that key, copies the next files in the order of their keys, and writes the cursor back. The cursor is in the backup bucket and not in D1 or KV, so a bucket that is new or was emptied is filled from the beginning with nothing reset by hand.
- **A file's key in R2 sorts after every key that is already there.** The cursor is one key, so a file that is stored under a key that sorts before it is never copied, and nothing says so. Step 6 makes a key start with a ULID, which sorts by when it was made. The `documents` table keeps a file's hash in `sha256`, apart from `r2_key`, so the same file is still found by its hash. One gap is left for step 6 to settle. A ULID is made before the bytes under it are in R2, and a run that lists R2 in between, and copies a file with a later key, passes that one by. Making the key as the bytes arrive, and not when the upload link is made, narrows it. Having the copy hold back from a file that was stored in the last few minutes, which R2 says for each file it lists, would close it.

## Considered options

- **Pull from outside:** a scheduled GitHub Action, or a machine of the User's own, that runs `wrangler d1 export` and uploads the result. No Workers limit would apply to it. But it is a second thing to set up and watch, it needs a Cloudflare token and the bucket's key kept somewhere else, and a machine of the User's own has to be on. Everyone who hosts an Attic would have to build the same.
- **A bucket in the same Cloudflare account:** R2 needs no signing and no second provider. It is lost with the account, and that is the loss the backup is for.
- **Let the Worker prune old exports:** it could keep the newest thirty. Then the key must be able to delete, and the worst a bug can do gets much worse. A lifecycle rule does the same at the provider.

## Consequences

- The run has to fit a cron run on Workers Free (ADR 0012): 10 ms of CPU, 15 minutes, and 50 subrequests. The export is streamed from Cloudflare into the bucket. It is never held in memory and never hashed, so its size costs no CPU. An S3 `PUT` has to say how long its body is before the first byte, which is the length the signed address gave, and its signature covers the headers and not the body (`UNSIGNED-PAYLOAD`).
- The chores of one run share the 50 subrequests. The run counts them in code and stops at 45. The export takes 22 at the most: up to 20 calls about the export, one read of the signed address, and one `PUT`. An export that is done at the first call takes 3. The files get what is left: 2 for the cursor, which is read and written back, and one for each file. A read from R2 is not one of the 50: Cloudflare counts a call to its own services apart (ADR 0012). So a run copies 40 files after an export that was done at the first call and 21 after the slowest one, and the rest wait for the next night. If the backfill of step 6 outruns that, the same trigger can fire more often.
- A file that fails stops the batch. The cursor is written at the last file that got there, so the one that failed is the first of the next night.
- A file is streamed with its length and never hashed in the Worker, like the export. R2 keeps the MD5 of a file that was stored in one piece, and the Worker sends it along as `Content-MD5`, under the signature. An S3 bucket turns a `PUT` away when its body does not have the MD5 it was sent with, so the bucket checks the bytes of a file at no CPU in the Worker. The export has no MD5, and neither has a file that was stored in parts, so those go unchecked.
- The access key has to read as well as write, because the cursor is read. Only a 404 means there is no cursor yet. Any other answer stops the copy, since starting from the beginning each night would copy the same files over and over. S3 answers 403 and not 404 for an object that is not there when the access key may not list the bucket. So at AWS, and at a provider that follows it in this, the access key has to be allowed to list too.
- An export blocks the database's other requests while it runs, so the run is at 3 in the morning in the configured timezone. A Cron Trigger is in UTC, so the hour is worked out at deploy from the timezone's standard time, and a deploy plans the same trigger in any season. Where the clocks change, the run is at 4 in the summer.
- The export is asked for with a Cloudflare API token of its own, which the User makes by hand. It is not the deploy token. Alchemy could make it, but the deploy token would then need the permission to create tokens.
- A night that fails only shows in the log: one line for each chore, with what it did, or with the status and the answer of whoever said no. Nothing is tried again before the next night, and a chore that fails does not stop the next. No secret and no signed address is logged.
- The backup is off unless it is configured. A deploy with none of its settings still has the trigger, and its run says the backup is off. A deploy with some of them and not all stops.
- `alchemy dev` backs nothing up to a real bucket, whatever `.env` holds. Its database and its files are local ones, and once local files were in the real bucket, the cursor would be past files of the deployment that are not in the backup yet. In dev mode the backup is on only for a bucket on this machine, which is where the tests' stand-in is.
- A request to the bucket is signed with `aws4fetch`, pinned. Signature Version 4 is not written by hand in the Worker.
- The trigger is one of the five an account gets on Workers Free. Every nightly chore hangs on it, so step 6 needs no second one.
- A backup is only as good as the restore that was run from it, and none has been run yet. That is issues 61 and 62.

Checked against Cloudflare's API reference for the D1 export and alchemy 2.0.0-beta.81 on 2026-10-13. The parts about the files were checked the same day, against the S3 API reference for `PutObject` (`Content-MD5`) and `GetObject` (the answer for an object that is not there), and the reference for R2's Workers API (the MD5 it keeps, and the order of a list). That reference does not name `startAfter` among the options of `list`. It is in the binding's types, R2's release notes speak of it, and the local simulator goes by it, so the second night of files on a deployment is the first real proof of it. That a read from R2 is not one of the 50 subrequests is from Cloudflare's limits page, as ADR 0012 says: only D1 was measured. A night with more than 25 files on a deployment proves it, and a run that is wrong about it fails in the log with what it had copied.
