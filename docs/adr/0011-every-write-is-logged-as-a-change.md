# Every write is logged as a Change, and undo works from the log

A model is the only writer, a merge patch with `null` removes keys, and deleting is routine (ADR 0009). D1's Time Travel can only restore the whole database, and only 7 days back on the Free plan. So every write also appends a Change to an append-only log, in the same atomic batch as the write itself (ADR 0006): the tool, the record, and the record as it was before and after. One `undo` tool puts a record back from a Change, including a deleted row.

## Considered options

- No log, relying on Time Travel: nothing to build, but undoing one bad write means rolling back everything written since.

## Consequences

- Changes are kept forever. They are small, and they answer "what did the bot change in that session".
- There is no separate history tool. A record's recent Changes come back with the record, and the log can be read with `query`.
- A deleted Document's file stays in storage for 30 days before a nightly sweep removes it, so undo can bring the file back inside that window. Deleting a file is therefore not immediate.
- A tool's batch never runs without a Change (issue 32). A tool is not handed the atomic batch. It hands its statements to one write, each with the record it is about, and the step that runs the batch is the step that adds the Change to it, under the tool's name. One call is one write. That covers what a tool does through the write. Nothing stops a tool from running a statement of its own outside it, and no tool should.
- A snapshot is read by a statement inside the batch, before the tool's statements and again after them. So it holds what was stored, defaults and merge patch included, and not what a tool meant to store.
- One place says what a record of each type is: its table, its columns, its link sets, and what it points at (`packages/core/src/records.ts`). Snapshots are built from it, and `undo` works from it (issue 36).
- A save that changes nothing still records a Change, because its statement still ran and moved `updated_at`. Its `before` and `after` differ in nothing else.
- A link set is written by statements about the record it belongs to, so the record's snapshots hold the set before and after (issue 34). An Item is 15 columns and one link set, which makes its snapshot 16 fields: the most one JSON object takes on D1 (ADR 0006). A sixteenth column on `items` stops the module from loading, and the snapshot has to be built in two parts before one can be added.
- Work is 14 columns and two link sets, its Items and its Spaces, so its snapshot is 16 fields as well (issue 35). A fifteenth column on `work` stops the module from loading in the same way. The `project` and `schedule_id` arguments that `log_work` is to take later set columns that are there already, `project_id` and `schedule_id`.
- `undo` works from the snapshots alone, and has no code for any one tool (issue 36). For each type it has a few statements that read the Change's rows of `change_records` inside the batch: one puts back the rows the Change deleted, one restores the rows it updated, one takes out the rows it created, and two more empty each link set and fill it again. So an undo is the same handful of statements whether the Change touched one record or two hundred. A statement that is about several records is handed to the write with each of them, and runs once.
- An undo restores every column, `created_at` and `updated_at` included, so a record is exactly as its snapshot had it. The undo is a Change of its own with `undoes` set, written by the same write as any other, so it has each record before and after and can be undone.
- An undo is refused when a later Change touched one of its records, and the error lists those Changes newest first. A Change and the undo of it leave the records as they were, so neither counts. Without that, each undo of a later Change would be one more later Change, and the way would never clear. A Change that was undone already is refused the same way, since its undo is the later Change, and the error says so.
- Before it takes a record out, `undo` asks what points at it. It goes by what each type says it points at in `records.ts`: the columns of its row, its link sets, and the type and id a Note is attached by. A record of the Change itself does not count. The foreign keys would not do this. Some would refuse the batch with no word on what is in the way. Others would delete what points at the record, or empty it, with no Change to say so. A test holds each type's list to the foreign keys of its tables. A column that points at a type no tool writes yet, such as the Project of Work, joins the list when that type does.
- The other side is checked the same way, which the issue did not list (issue 36). A record that an undo brings back may have pointed at one that another undo has since taken out, and it may have had a name that another record has now. The database would refuse most of those batches whole, and the client would be told only that the call failed. One it would not refuse: a Note is attached by type and id with no foreign key, so a Note could be put back on an Item that is not there. Each was reproduced with the write tools there are, in four or five calls. So `undo` reads all three before it writes, in one statement, and each refusal names the records and says what to undo first. `records.ts` says which columns no two records of a type can share, and a test holds that to the unique indexes of its table.
- With those checks, a batch of an undo that the database refuses is a mistake in the code or the data, not something a client can fix, and it is logged as any other unexpected failure is.
- Pointers and names are what the database can state. Two rules are known only to a save's code, and `undo` first went through where a save would have refused or kept two records in step (issue 36). A Category could end up under itself by way of another: its parent is cleared, that parent is put under it, and the clearing is undone. And a Note could be left at the Property its record was at: an Item moves, a Note is added to it there, and the move is undone, which takes the Item back and leaves the Note. In each, the later Change touched another record, so no later Change stood in the way. `undo` now refuses both (issue 46), in the same statement it reads what else blocks it with, and still has no code for any one type. Every read that statement can hold is in one list, which the guard on its length is built from too (ADR 0006), so a new read cannot be made and left out of the guard.
- A loop is looked for in the tree as it would be once the undo is done: each record the undo brings back under what it was under before, and every other record under what it is under now. `undo` walks up from each record it brings back, and a walk that comes round to where it began is a loop. It goes by `records.ts`, where a Category is the one type with a pointer column of its own type. The error names every Category on the way round. It names no tool, since nothing in `records.ts` says which tool saves a type. The description of `undo` names `save_category`. One of the others has to come out from under its parent first, since saving one that the Change touched would be a later Change in the way. A loop that is there already, and that the undo only brings a Category back under or into, was not looked for or mended: the walk stops at it, and a Category that is in it cannot be brought back until it is mended with `save_category`.
- For the Note there were two answers, and refusing was chosen over moving the Note along (issue 46). An undo is refused while a Note that is not a record of the Change is on a record the undo would move to another Property. The error names the Note and the Change that added it, and once that Change is undone the way is clear. So `undo` still writes only to the records of the Change it undoes, and its reply keeps its three lists. Moving the Note would have had the undo write to a record the Change never touched. The cost is that the Note has to be added again afterwards. A Note that moved in the Change itself is one of its records, and goes back with its record as before. The read does not ask whether the Note and its record were at one Property to begin with. Where an earlier undo already left a Note behind, an undo that would take its record back to it is refused like any other, and undoing the Change that added the Note still clears the way.
- The Note is held from the other side too, which the issue did not list (issue 46). A Note that an undo brings back comes back at the Property it was at, and the record it is on may have moved while the Note was out: a Note is added to an Item, that is undone, the Item moves, and the undo is undone. That was reproduced with the write tools there are, in five calls, and left the Note at the Property the Item had left. So an undo is refused when a Note it brings back is on a record that is not one of the Change's and is at another Property now. The error names the Note, the record, and the latest Change that moved the record. Undoing that Change clears the way, and so does moving the record back. The way the first refusal gives leads straight here: the later Note is taken out, the move is undone, and then the undo that took the Note out is undone. Without this side, that put the Note back at the Property its record had just left.
- `records.ts` says which column a Note follows its record in: `follows`, beside the columns it is attached by. No key or check in the database holds a Note to the Property of its record, so a test can only hold the column to pointing at one type in both tables. A Vendor has no such column, and a Note on one is at no Property.
- A Change that takes a name from one record and gives it to another cannot be undone: one that deletes a Vendor and makes another under its name, say. An undo brings rows back before it takes rows out, because a key that deletes or empties what points at a row does so the moment the row goes, and the name is still on the other record then. `undo` refuses it and says it cannot be undone, where it once told the client to undo the very Change it was undoing. No tool makes such a Change. A tool that replaces a record has to update it in place. Otherwise the order has to change first, which would take deferring the foreign keys of the batch (ADR 0006).
