# Each write is reads first, then one atomic batch

D1 has no interactive transactions, and `@effect/sql-d1` dies with a defect if `withTransaction` is called (checked against 4.0.2 on 2026-10-09). So every write tool does its reads first, builds all of its statements, and sends them as one atomic batch. Core reaches this through a small atomic-write service with two implementations: D1's batch in the Worker, and an ordinary transaction in the Node SQLite tests.

## Considered options

- Non-atomic writes, ordered so a failure leaves only harmless leftovers: simpler, but a half-written record is hard to notice in a database that only a model writes to.
- Dropping Node SQLite and testing only on local D1: closer to production, but slower tests and a core package tied to the Workers runtime.

## Consequences

- Never call `withTransaction` in `packages/core/src`. The transaction that stands in for the batch lives with the Node SQLite tests.
- A write cannot read back its own earlier statements. Ids are ULIDs generated in code, so every statement can be written before any of them runs.
- Space and Vendor names get case-insensitive unique indexes, so "create on first use" cannot produce both "Kitchen" and "kitchen".
- Node SQLite and D1 are not the same build, so a small smoke suite runs the real migration on local D1. It must cover the recursive category view, which is valid SQLite but was not confirmed on D1.
- `query` is the one tool that does not run on Node SQLite. D1 says whether a statement changed the database only in its own result (`meta.changed_db`), so `query` asks the driver for that result and reads it as D1's (issue 24). Its guard also leans on how D1 treats a string of several statements. It is tested through the real Worker on local D1, and the check on `changed_db` with a stand-in driver.
- D1 has limits that Node SQLite does not, and a statement that breaks one passes every test in core. `search` met two (issue 25). D1 takes at most five SELECTs in one UNION, which its limits page does not mention and which was found on local D1 on 2026-10-10. It also takes at most 50 bytes in a `LIKE` pattern (ADR 0003). Neither shows up on Node SQLite. The tests of `search` that go through the real Worker on local D1 are what hold them.
- One limit on D1's limits page does not show up on local D1 either: 32 arguments to a SQL function. Local D1 took 100 on 2026-10-10 (issue 26). `get_record` builds each list with `json_object`, two arguments to a field, so no test can hold that one. The code that builds an entry refuses more than 16 fields.
- The atomic-write service is `AtomicBatch` in `packages/core/src/write.ts` (issue 32). No tool is handed it. A tool writes through `Write`, which the tool frame builds for each call and which adds the Change to the batch (ADR 0011).
- That a batch is all or nothing is tested with a trigger that refuses a row partway through, on Node SQLite and through the real Worker on local D1. Local D1 took the trigger on 2026-10-11, and the `INSERT ... SELECT ... ON CONFLICT DO UPDATE` that writes a Change's snapshots.
- Creating a Space or a Vendor on first use is a read and then an INSERT in the caller's batch (issue 33). Two calls that name the same new Space at the same moment would both find none. The unique index then refuses the second batch whole, so that call fails and leaves nothing behind, and calling it again finds the Space. One deployment serves one User, so this is left as it is. The check that a Category's parent makes no loop is a read before the batch in the same way, so two saves at the same moment could each pass it and make a loop between them. Whatever walks the Category tree already stops at a loop.
- A call that names the same new Space or Vendor more than once has to ask for it once. Each ask that finds none hands back an INSERT, and two of them in one batch would be refused the same way. A tool that takes a list asks through `spaceOrNewOnce` and `vendorOrNewOnce`, which sit beside `spaceOrNew` and `vendorOrNew` (issue 35). They are built on `referredOnce` in `packages/core/src/save.ts`, which hands the INSERT to the first entry that names the record and none to the rest (issue 34). It tells two names apart the way the database does, by `nameKey`: case is ignored for the letters A to Z and for nothing else.
- A list is one batch however long it is. `save_item` with 50 new Items is more than sixty statements, and local D1 took it on 2026-10-11, with the `INSERT ... SELECT ... FROM json_each` that fills an Item's extra Categories (issue 34). The reads before the batch do not grow with the list: the Items a list updates are read in one query, and each Property, Space, and Vendor once.
- `log_work` with 50 new pieces of Work, each with an Item, two Spaces, and a Note, is more than two hundred statements in one batch, and local D1 took it on 2026-10-11 (issue 35). Its reads do not grow with the list either: the Work a list updates is read in one query, the Items it names in another, and each Property, Space, and Vendor once.
- The batch of an undo goes in an order the foreign keys allow (issue 36). Rows are put back with a type after the types it points at, then rows are restored, then rows are taken out in the other order. A row is restored before the rows it no longer points at go out, because a key that deletes or empties what points at a row does so the moment the row goes. Each statement is about every row of one type, and SQLite holds a statement to the foreign keys only once it is done. So a Category goes in or out with the one it is under, whichever row comes first. Local D1 did both on 2026-10-11: two statements in the wrong order were refused, and one statement with its rows in the wrong order was taken.
- D1 can defer the foreign keys of a batch, with `PRAGMA defer_foreign_keys = on` as its first statement. Its docs describe this for a transaction and say nothing of a batch. Local D1 took it on 2026-10-11, and refused the batch whole when a row still pointed at nothing at the end. `undo` does not use it: the order above needs nothing that D1 has and Node SQLite lacks.
- The statements of an undo read a Change's own JSON inside the batch: an `UPDATE ... FROM`, an `INSERT ... SELECT` over `json_extract`, and a join on `json_each` for a link set. The read before them compares a pair of columns, `(created_at, id) > (...)`. Local D1 took them all on 2026-10-11.
- D1 takes a statement of up to 100,000 bytes, and each statement of a batch the same (its limits page, read on 2026-10-12). Nothing was sent to local D1 to see whether it holds to that, so no test can. The longest statement Attic builds is the one `undo` reads what blocks it with: a JSON column for each way a record can point at another, two times over, and one for each type with a name to itself. With every one of them in it, it is 35 columns and about 31,000 bytes, and each new way of pointing adds about 1,800 (issue 36). `compact` in `packages/core/src/sql.ts` refuses a statement over the limit, and `undo` builds its longest when the module loads, so a type too many stops there and not at the undo of a Change that touched everything.
- That statement now also walks the Category tree, and reads the Notes an undo would leave at another Property than their record, from either side (issue 46). It is 42 columns and about 39,000 bytes with every read in it. The walk is a recursive query inside one of the columns: two tables in a `WITH RECURSIVE`, each a `UNION ALL` of two SELECTs, with the id of the Change bound inside it. So no UNION in the statement has more than two SELECTs, under the five D1 takes. Local D1 took the walk on 2026-10-12, through `query` first and then through `undo` itself. A recursive query that meets a loop it cannot leave never ends, so a walk is no longer than there are Categories. The check that a Category's parent makes no loop is still a read before the batch, so two saves at the same moment can still make one, and an undo then stops at it as everything else that walks the tree does.
- With a Project and a Quote among the types, that statement is 57 columns and about 55,900 bytes with every read in it (issue 50, measured on 2026-10-12), under the guard of 100,000. Fifteen columns are new: two for each of the six new ways of pointing, one for a Quote's Project and Vendor being its own, and two for a Note on a Project. A way of pointing still adds about 1,800 bytes. One where the record that points is a Quote adds about 2,800, because a Quote has no column to be named by. Its name is a lookup for its Vendor and one for its Project, and each of those asks the Change's own snapshots before it asks the table (ADR 0011). No UNION in it has more than two SELECTs. An undo makes only the reads that can matter to its Change, so the whole of it is sent only for a Change that touched every type.
- Local D1 took what the two types brought on 2026-10-12, through the tools themselves: a Quote's name read inside a column of that statement, as subqueries joined with `||` under a `coalesce`, with the id of the Change bound inside them, and the read `get_record` finds a Quote's Changes with, which holds the Project's id against `json_extract` of both snapshots of a row of `change_records`.
- The batch of a delete goes in an order the foreign keys allow too (issue 51). What uses the record comes first: each record that points at it is pointed at the replacement, or loses its link to it. Then the Notes on the record move to the replacement. Then rows go out with a type before the types it points at, Notes first, and each row after what it has in its own link sets. So nothing points at a row when it goes, and `delete_record` leans on no key that acts.
- What each key does when the row it points at goes, read from `migrations/0001_init.sql` on 2026-10-12. It does nothing where the row is a Vendor, a Space, a Category, or a Project, so that row cannot go while anything points at it: an Item, a Quote, Work, or a Document at a Vendor, an Item and the link tables of Work and of a Project at a Space, a Category, an Item, and an Item's link table at a Category, a Quote and Work at a Project. It deletes the row that points (`CASCADE`) in a link table on the side of the record the set belongs to (`item_categories.item_id`, `work_items.work_id`, `work_spaces.work_id`, `project_spaces.project_id`), in `work_items.item_id`, in `schedules.item_id`, in `document_links.document_id`, and from a Space, a Project, a Schedule, Work, and a Note to their Property. It empties the column (`SET NULL`) in `work.schedule_id`, and from an Item and a Document to their Property. A Note and a Document's link point by type and id, and no key holds either. The two keys of the Change log are not in a delete's way, since no tool deletes a Change: an undo's pointer at the Change it undid does nothing, and a Change's records go with it.
- So an Item is the one record a delete takes out where a key would act on a row of another record: its links from Work, and its Schedules. `delete_record` deletes the links itself, as steps about that Work, before the Item's row goes. It refuses an Item with a Schedule until a tool writes Schedules, and it empties each record's own link sets itself too. A test runs deletes with the foreign keys off, where nothing acts but the tool's own statements.
- Local D1 took the statements of a delete on 2026-10-12, through the tool itself. The read names the records that go in a `WITH` of two SELECTs under one `UNION ALL`, and reads from it in three of its JSON columns. The batch has an `UPDATE OR IGNORE` on a link table, which is how a record that had both keeps the replacement once, a `DELETE` whose `WHERE` asks another table, and a `DELETE ... WHERE id IN (SELECT value FROM json_each(?))` for the rows that go.
- `gaps` reads everything it reports in one statement, after the read that finds the Property (issue 52). So a call is two reads, however many Items the Property has. The statement joins the `item_in_category` view, which walks the Category tree, to `json_each` over each Category's `expects` and over each Item's `data`. It numbers its rows with `row_number()`, and builds each list in a subquery over a `WITH` table that the statement reads several times. Local D1 took it on 2026-10-12, through the tool itself, with the Space bound and with it left null. It has no UNION, and is about 3,400 bytes.
