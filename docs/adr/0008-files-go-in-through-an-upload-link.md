# Files go in through a short-lived upload link

An MCP client can show the model a file but cannot hand the raw bytes to a server, and base64 in tool arguments does not survive real photo sizes. So a tool returns a signed link that lasts 15 minutes. A person opens it and picks files on a bare page served by the Worker, and a client with a shell posts the file to the same link. The Document is created when the bytes arrive, carrying the kind, date, total, text, and links the model supplied when it asked for the link.

## Consequences

- In a chat client the User handles a file twice: once to show the model, once to upload.
- Files are never sent back to the model. Some clients cap tool results too small for a photo (about 150,000 characters in claude.ai), and not every client passes images through. Viewing a file is a short-lived link the User opens.
- Reading the text out of a file on the server would remove the double handling. It is deferred because it adds an AI dependency.
- The request waits in D1, in `upload_requests`, until its link runs out (issue 65). The link is asked for from the client's server and opened a moment later from the User's phone, in another location. KV's docs say a change "may take up to 60 seconds or more to be visible in other global network locations", so the link could look as if it had run out. Workers Free also caps KV at 1,000 writes a day, which the OAuth provider already spends (ADR 0012). A request is not a record, and no Change has one. Asking for a link deletes the ones that have run out.
- The link is signed with HMAC-SHA-256 over its path and when it runs out, with a key Alchemy makes once and keeps, as it does the consent page's. So there is nothing to set up. The path is in what is signed, so a link to one page cannot stand in for another. The upload path is outside the OAuth provider, since a phone that taps the link has no token, and the signature is checked before anything is read.
- A file is posted on its own, with its type in `content-type` and its SHA-256 in `x-content-sha256`. The page works the hash out in the browser, and a client with a shell sends it the same way. The Worker streams the body into R2 with the `sha256` option, under a key that is the new Document's id, which is a ULID, so keys sort by when they were written. A request body with a `content-length` is a stream of a known length, which is what R2's `put` asks for.
- R2's docs say the hash is used to check the received object's integrity, and do not say what a mismatch does. Local R2 refuses the `put` with R2's error 10037, "The SHA-256 checksum you specified did not match what we received", and stores nothing (checked on 2026-11-04, and held by a test through the Worker). The Worker turns that into a refusal the sender sees, and writes no Document.
- The reads come first, then the file goes into R2, then the Document is written as one Change, under the name of `request_upload_link`. So a file R2 will not take leaves no Document. A write that fails after the file is in R2 leaves a file with no Document, which the sweep that is still to come removes. A file Attic has already, by its hash, is not stored again: its Document is attached to the new records too, and its empty fields are filled in from the new request. What it says already stays, since it was read from the same file.
- A file is a JPEG, PNG, WebP, HEIC, GIF, or PDF, up to 25 MB, and the Worker refuses anything else from the headers alone. HEIC is taken as `image/heif` too, which is what some systems call it. Not SVG, which is a page that can run script, and a Document's file is to be opened from Attic's own address (issue 66).
